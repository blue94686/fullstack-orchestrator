# Stitch, Gemini model and frontend quality

Read this when a task needs Stitch design, direct Antigravity/Stitch access or visual-quality acceptance. These are separate roles: Gemini is a model, Antigravity CLI/Desktop and Gemini Desktop are execution clients, Stitch is a design service, and MCP is a tool transport. A model cannot connect itself to Stitch without a client/tool connection. Record executor software, transport, observable model, actual tool connection and design artifact identity separately. Do not assume CLI inherits Desktop MCP configuration, tools or authentication. Preserve existing model and effort settings; the user's general Gemini design preference is not permission to silently replace a configured model. Record the selected model if already available; ask only when a necessary setting change requires a choice.

## Supported integration and present evidence

The official [Google Labs Stitch Skills repository](https://github.com/google-labs-code/stitch-skills) describes MCP workflows for creating screens from text/images, editing screens, listing designs/screens, and downloading generated HTML and screenshots. The official [Google Codelab](https://codelabs.developers.google.com/design-to-code-with-antigravity-stitch) also describes an Antigravity IDE MCP integration. These document possible integrations, not this Codex session's live connectivity, available tool schemas, permissions, target-project access or CLI/Desktop parity. Discover the connected Codex MCP tools at runtime and verify the exact operations needed; never infer connection or capability from repository docs or an installed skill.

## Official Stitch skill ownership

Use the [official Google Labs Stitch Skills](https://github.com/google-labs-code/stitch-skills) for Stitch-specific prompt construction and MCP tool sequences when installed and available in the active Codex session. Prefer only `stitch-design` for design creation/edit/retrieval. Add `stitch-build` or `stitch-utilities` only when their described capability is required by the task; do not install the whole suite by default. The official `stitch::generate-design` skill documents text/image generation, screen editing/variants, screen listing and downloading generated HTML/screenshots. Let that skill's current instructions and the live MCP schema own those details; this orchestrator only decides when to invoke it, supplies the bounded product brief, preserves project authorization, and verifies the returned artifacts. Do not duplicate upstream prompt templates or MCP call recipes here.

The official repository states Codex supports its plugin marketplace. Follow its current Codex marketplace/install instructions when the official integration is authorized. Plugin installation and MCP connection are separate. Do not run global marketplace/plugin installation commands under project-scoped permission. A user request to connect the official MCP authorizes only the minimum connection configuration; it does not authorize creating credentials, accepting terms, billing changes or unrelated global settings. If the plugin is absent, record it as unavailable and continue through an already authorized Stitch transport. React-specific build guidance does not authorize migrating a Vue or other existing stack. A Skill's declared tools are not authentication or live MCP capability.

Stitch service authentication is separate from a paid Gemini model API. Authorization for Antigravity/Gemini Desktop does not grant creating keys, sharing private designs or accepting new terms. A direct user request to connect authorizes the minimum global MCP configuration for that service; keep a redacted backup and rollback, preserve every unrelated setting, and never persist secrets in task records or this skill. Codex remote MCP supports `env_http_headers` for reading custom header values from the Codex process environment; see [Codex MCP configuration](https://developers.openai.com/codex/mcp/). If required credentials are not already securely available to that process, stop before connection configuration and give the user the official account-side setup step. Never ask the user to paste a key into chat or write a secret literally into Codex config.

## Select the actual design path

Resolve current availability and long-term preference from [project policy](project-policy.md): Antigravity is temporarily unavailable, so do not probe it or configure its MCP while that blocker remains. Use needed Stitch exports with the task-selected authorized frontend route. The Antigravity integration options below require the policy’s restoration conditions and actual connection verification before use.

1. Prefer a callable, authorized Stitch MCP exposed directly to Codex when it supports the required design operation. Use it to inspect existing project/screens, generate or edit only requested screens, and collect actual design resources (for example HTML/screenshot outputs) with identifiers or hashes. This path is independent of Antigravity availability and does not require routing the same design request through another Gemini client.
2. Use Stitch Desktop when MCP is unavailable, lacks the needed operation or project access, or the user selects the desktop UI. Missing Stitch MCP does not mean Antigravity engineering is unavailable and does not justify switching to Gemini Desktop.
3. After design assets are collected, select the authorized frontend executor separately. If Antigravity as a whole is unavailable, Gemini Desktop Work/Task may receive the minimum approved design files and contract. Verify its actual engineering/file capability. Do not infer its MCP support from model branding.
4. If design generation/export itself is blocked, continue independent requirements/backend work. Preserve existing designs; do not have Codex silently substitute visual design or create a demo merely to pass a gate.

Before a write, bind the exact design project/screens and permitted operations. Exports carry provider versions where available, otherwise file hashes and the limitation. A new screen candidate cannot overwrite an accepted design without scope review. A screenshot establishes appearance only; source/resources and working interactions need their own evidence.

Before export, read back the selected screen list, format and destination. A provider's default export may open another builder or publishing service; select the authorized local-file format when file exchange is intended. Do not infer that a downloaded HTML package includes every remotely referenced asset. Verify archive contents and actual files separately from design acceptance: a successful export of a rejected candidate proves transport only and must not unblock frontend implementation.

For MCP, check the tool's project/screen scope before generation or edits, request only the minimal affected screens, and preserve accepted designs. Read/retrieval can be preferred for reuse without invoking generation. Let the official skill select concrete tool calls; record actual tools called and returned resource IDs/files, not the model's description of them. Validate HTML/screenshots for missing external assets; a generated design is a candidate that Main checks against the brief before frontend implementation. Keep the brief concise and specific to affected flows, states and existing design tokens to reduce redundant iterations.

## Design brief and acceptance

Keep a compact brief in existing project records: affected user flows/pages, real content and data density, reference direction, existing brand/tokens, viewport targets, applicable keyboard/focus/contrast behavior and required states. Cover loading, empty, error, permission, validation and submission states where affected. Main resolves routine choices in scope; only material unresolved choices go to the user. No mandatory multiple variants or manual gate for every task.

Return actual design resources/tokens, page/action mapping and constraints with the frontend handoff. Check design-to-implementation consistency on the integrated candidate at affected viewports, including typography, spacing, content, interaction states and assets. Record functional checks separately from visual comparison. Frontend errors return to the frontend owner; Codex may integrate shared contract/client wiring within its assigned scope, but cannot silently take over a user-exclusive visual implementation task or count its own work as Antigravity success.

No claim of pixel accuracy from a build, no claim of better UI from merely selecting Gemini, and no backend authorization/business logic inferred from generated controls. This workflow improves the assignment and acceptance of design work; it does not change the Codex application's own UI.

## Google AI Studio Build (optional)

AI Studio Build is a cloud execution surface, distinct from the Gemini model, Gemini Desktop and Antigravity. It is available as a task-selected frontend candidate/preview route, not a mandatory stage or an automatic fallback. Existing project defaults remain in force. Record `AI_STUDIO_BUILD` with the actual browser/tool transport, cloud project/task locator, observable model, supplied input/design/contract versions and returned artifact hashes. Verify current account access, Build capability, export and available cancellation/status methods before dispatch; inclusion in this skill is not runtime evidence.

Use accepted Stitch resources or an existing accepted design with the minimum relevant sanitized specification, source and contracts. A rejected design may be transferred only for an explicitly scoped repair or transport test and cannot unblock implementation. Cloud projects do not inherit local `shared/`, installed skills, dependencies or filesystem grants. Main deliberately supplies authorized inputs and collects downloaded files into the invoking product's `shared/artifacts/<executor>/<task>/<attempt>/`; keep different products' cloud projects, conversations and exports separate. Do not upload credentials, private datasets or unrelated repositories. A required sensitive disclosure or new permission must receive its corresponding authorization.

Prefer preview and local source ZIP handoff. Before acting on Stitch's AI Studio export, confirm the selected screens and destination and inspect any terms/access prompt. GitHub connection/sync, public sharing, cloud deployment, billing, API key creation and configuration changes are separate operations governed by their applicable authorization; adding this route does not authorize them. Preserve account/model/settings. Do not add Gemini API calls, cloud storage, authentication or hosted backend merely because Build offers them.

For an existing product, preserve the actual stack and authoritative contracts. Export to staging; inspect archive paths, generated scripts, dependencies, network calls, secret placeholders and changed files before running or integrating. Generated backend code is a proposal for Codex review, not a reassignment of backend/database/communication ownership. Main checks scope and design acceptance, adapts only compatible scoped changes, then runs affected local checks against the final candidate. Cloud preview or successful export cannot establish local reproducibility, real business integration or production readiness. Record missing remote assets and Mock boundaries.

Apply the existing one-attempt submission, observation, reconciliation, retry and acceptance protocol. Before switching from Gemini Desktop or another executor, reconcile its task and resolve any partial output. AI Studio cannot be used to bypass authentication, quota or policy restrictions; independently authorized permitted work remains subject to its own access controls. If Build cannot return retrievable source, classify it as advisory/preview capability rather than verified engineering execution. Do not create an adapter service, lock or global registry for this route.
